# Bug 118 joins the v0.6.0 cut set (2026-10-20)

**Decided by:** Philip, 2026-10-20 · **Status:** Decided
**Led to:** Bug 118 moved into the "v0.6.0 cut set" group of PLAN.md Next Up, ahead of Bug 34

## What prompted it
The review of PR 69 (Bugs 113, 114) found a segfault and filed it as Bug 118, outside
the cut set, described as "a `String` parameter's `s.len()` crashes". Re-probing it the
same day showed the trigger is wider: any `String` made by calling `.to_string()` on a
plain `string` crashes the program the first time it is used, with no function call
involved, both in a native build and under `klar run`. Only the tree-walking
interpreter runs it correctly. The question put to Philip: should it join the v0.6.0
must-fix list?

## What we weighed
- **Add it to the cut set** — the release waits on it. Converting a `string` to a
  `String` is an ordinary thing for a trial program to do, and the failure is a crash
  with no error message, which is the class of defect the cut set exists to remove.
- **Leave it outside the cut set** — it stays first among the crashes found after the
  cut set was chosen, and v0.6.0 lists it under Known issues with the workaround
  `String.from(...)`. Lost: a trial user has no reason to know the workaround, and a
  crash on a common conversion undercuts the "no surprises" claim the trial tests.

## What we decided, and why
Add it to the cut set (Philip chose option 1, the recommendation). The cut set's test
is whether a trial program would plausibly hit the defect and get a crash or a wrong
answer with no warning; this one passes it more clearly than the bugs added on
2026-10-17, since the trigger is a single common method call.

## What it does not settle
Whether other conversions that produce a `String` (for example `.to_string()` on other
types) share the cause; `42.to_string()` works, so the fix's own probes decide that.
Whether the bytecode VM and native backends share one root cause is for the fix to find.
