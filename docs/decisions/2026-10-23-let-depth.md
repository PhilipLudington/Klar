# `let` freezes the whole value, its elements and fields included (2026-10-23)

**Decided by:** Philip, 2026-10-23 · **Status:** Decided
**Led to:** Bug 130 (taken off deferral, top of Next Up)

## What prompted it
PR 76 (Bug 63) made `x = 2` on a `let` a check error but left `a[0] = 9` and `p.x = 5`
allowed, filing the rest as Bug 130, because refusing them rejects 8 tracked files. It
also made the REPL, which had refused those writes, allow them. A side agent: "Whether
`let` should block these changes is a language-design call for you to make." Philip had
believed this was settled. It was, in January: the first checker's `isMutable` refuses
any write rooted in a `let`, but it was wired only to a path files never use.

## What we weighed
- **Deep everywhere** (Rust, D; C++ for values): every write rooted in a `let` or a
  by-value parameter is refused. Costs the stdlib collections `inout self` on their
  mutating methods, and `var` on their callers' bindings.
- **Deep for values, shallow for List/Map/String handles** (Swift's rule for classes):
  keeps the stdlib as it is. Rejected: it rests on List copies sharing storage, which the
  2026-10-18 move/clone decision already called a bug, so the stdlib needs `inout self`
  either way.
- **Binding only** (JavaScript `const`, Java `final`, Kotlin `val`): `let` stops only
  re-pointing the name. Rejected: those languages' collections are shared references;
  every language with move or value semantics freezes them.

## What we decided, and why
Deep everywhere, as the January design intended. Mutation is visible at both ends, with
`var` where the value lives and `inout` where a function changes it, which fits "the
code explains itself". It also matches the move/clone decision.

## What it does not settle
Whether `Cell` stays the one way to change something behind a `let` (as in Rust), and how
it is freed (2026-10-22-cell-storage-deferred.md).
